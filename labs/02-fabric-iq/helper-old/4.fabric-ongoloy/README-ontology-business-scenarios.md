# 온톨로지 비즈니스 질문 v2

## 이 문서의 목적

데이터 에이전트 질문 중 **일반 NL2SQL로는 답할 수 없는 것**을 시연하기 위한 질문 설계입니다. 온톨로지가 실제로 더하는 값이 무엇인지 [온톨로지 생성 노트북](manufacturing_ontology.ipynb)의 정의에서 확인하고, 그 값을 사용하는 질문만 남겼습니다.

각 코드 블록 전체를 **새 대화에서 한 번에** 전달합니다. 사전 질문·대상 ID 선택·앞선 답변이 필요하지 않습니다. 블록 아래의 기술 설명은 진행자용이며 질문에 붙여 넣지 않습니다.

## 현재 검증 상태

| 계층 | 상태 | 근거 |
|---|---|---|
| 온톨로지 정의 게시 | 확인됨 | Fabric Explorer에 11개 엔터티 표시 |
| Graph 인스턴스 | 확인됨 | 엔터티 Overview에 속성 분포 표시 |
| 단일 엔터티 조회 (질문 0) | **동작 확인** | 사용자 실행 |
| QMS 내부 관계 (질문 1·2) | **동작 확인** | `NcrHasDisposition`, `InspectorDoesInspection`, `InspectorRecordsMeasure` |
| MES 내부 관계 | **동작 확인** | Graph 쿼리에서 `EquipmentHasRuns` 5행 반환 |
| **MES↔QMS 교차 관계 6개** | **전부 실패** | Graph 쿼리 직접 실행에서 확인. 아래 4단계 참조 |
| FDC 시계열 (질문 5) | 미확인 | 노트북도 미검증으로 명시 |

**교차 관계는 하나도 동작하지 않습니다.** 에이전트가 아니라 Fabric Graph 쿼리 편집기에서 직접 실행해도 같은 오류가 납니다. 따라서 에이전트 구성·질문 문구·권한의 문제가 아닙니다.

## 1단계: 모델이 실제로 더하는 값

| 영역 | 엔터티와 바인딩 | 표현하는 내용 |
|---|---|---|
| MES | Equipment, ProductionLot, ProcessRun. 각각 MES 테이블에 정적 바인딩 | 설비 유형, 로트·제품 코드, 공정실행·시간 구간 |
| QMS 검사 | Inspector, Inspection, Measurement, InspectionSpec | 검사·측정 담당 역할, 판정, 실제 측정과 적용 규격 |
| QMS 품질 조치 | DefectCode, IncomingInspection, Nonconformance, Disposition | 결함 분류, 입고검사, 부적합·원인 기록, 처리·승인·비용 |
| FDC | Equipment에 6개 시계열 속성 바인딩 | 센서 코드·단위·측정 시각·값·상태·가동 상태 |

총 11개 엔터티는 11개 MES·QMS 테이블에 정적으로 바인딩됩니다. FDC는 별도 엔터티가 아닙니다. `fdc_sensor_spec`은 원본 검사에만 사용하며 온톨로지 규격 엔터티가 아닙니다. 시계열의 공정 시간 매칭, 유사 온도 범위, 인과관계는 정적 관계만으로 결정되지 않습니다.

### 모델에는 파생 의미가 없습니다

노트북의 `ENTITY_SPECS`는 각 엔터티에 **원본 테이블 하나의 모든 컬럼을 그대로 속성으로 복사**합니다. `RELATION_SPECS`의 18개 관계도 전부 원본 FK 컬럼을 매핑 테이블로 쓰는 직접 조인입니다. 계산 속성·상속·추론 규칙이 없습니다.

따라서 **온톨로지라서 새로 생기는 값은 없습니다.** NL2SQL 대비 남는 차별점은 셋뿐입니다.

| 차별점 | 모델 근거 |
|---|---|
| **이종 저장소 통합** | MES Lakehouse · QMS Lakehouse · Eventhouse(Kusto)를 한 그래프로 연결. 단일 소스 SQL로는 불가능 |
| **역할이 구분된 조인 경로** | `InspectorDoesInspection`(`inspector_id`)와 `InspectorRecordsMeasure`(`measured_by`)가 같은 Inspector를 서로 다른 역할로 연결 |
| **잘못된 조인 차단** | 엔터티 설명에 경고가 포함됨. 예: `metrology_eqp_id`는 생산 설비가 아님, `mes_defect_code`는 분류 매핑, 공급업체 로트는 실제 투입 근거가 아님 |

### 관계는 저장소 경계로 나뉩니다

`lakehouse_source()`가 테이블 접두사로 Lakehouse를 결정하므로 18개 관계는 다음과 같이 갈립니다.

| 구분 | 관계 | 개수 |
|---|---|---|
| MES 내부 | LotHasRuns, EquipmentHasRuns | 2 |
| QMS 내부 | InspectorDoesInspection, InspectorRecordsMeasure, InspectorDoesIncoming, SpecGovernsMeasurement, InspectionHasMeasures, DefectInIncoming, DefectInNcr, InspectionHasNcr, IncomingHasNcr, NcrHasDisposition | 10 |
| **MES ↔ QMS 교차** | RunHasInspection, LotHasInspection, EquipmentHasInspection, LotHasNcr, EquipmentHasNcr, LotHasDisposition | **6** |

QMS 내부 10개는 같은 Lakehouse 안의 조인이므로 NL2SQL이 그대로 수행합니다. 데모 차별성은 **교차 6개와 FDC 시계열 바인딩**에서만 나옵니다.

### 교차 관계 중에서도 로트 경유는 값을 더하지 않습니다

`mes_lot`의 컬럼은 `lot_id`, `product_code` 두 개뿐이고, 이 둘은 QMS 테이블에 모두 복사되어 있습니다.

| 교차 관계 | 상대에서 얻는 MES 전용 값 | 데모 가치 |
|---|---|---|
| `RunHasInspection` | `in_time`, `out_time` | **있음** |
| `EquipmentHasInspection` | `eqp_type` | **있음** |
| `EquipmentHasNcr` | `eqp_type` | **있음** |
| `LotHasInspection` | 없음 | 없음 |
| `LotHasNcr` | 없음 | 없음 |
| `LotHasDisposition` | 없음 | 없음 |

**MES 전용 값은 `Equipment.eqp_type`과 `ProcessRun.in_time`/`out_time` 둘뿐입니다.** v2 질문은 이 둘을 요구해 QMS 단독 우회를 막습니다. 로트 기준 질문은 관계를 걸어도 NL2SQL과 결과가 같습니다.

### 이름을 추측하면 실패합니다

노트북의 `property_name()`은 속성명이 26자를 넘으면 앞 19자에 SHA256 6자리를 붙여 잘라냅니다. 다음 4개가 해당합니다.

| 원래 이름 | 결과 |
|---|---|
| `Person_certified_characteristics` | 해시 절단 |
| `Spec_characteristic_name_ko` | 해시 절단 |
| `Meas_characteristic_name_ko` | 해시 절단 |
| `Disp_effectiveness_check_date` | 해시 절단 |

질문에서 측정 특성을 다룰 때는 `characteristic_name_ko` 대신 `characteristic_code`를 쓰도록 유도합니다. 이름을 늘리려면 온톨로지 재게시가 필요하므로 **모델은 수정하지 않고 질문에서 회피합니다.**

## 3단계: 데모 질문 6개

질문은 **위험도 오름차순**으로 배치했습니다. 앞 질문이 실패하면 뒤 질문을 시도하지 않고 원인을 먼저 확인합니다.

| 순서 | 질문 | 사용 관계 | 저장소 | 현재 상태 |
|---|---|---|---|---|
| 0 | 부적합 분포 | 0 | QMS | **동작 확인** |
| 1 | 처리 승인 상태 | 1 | QMS 내부 | **동작 확인** |
| 2 | 담당 역할 구분 | 2 | QMS 내부 | **동작 확인** |
| 3 | 설비 유형별 공정·검사 | 2 | **교차** | **사용 불가** — `RunHasInspection` 실패 |
| 4 | 설비 유형별 부적합 | 3 | **교차** | **사용 불가** — 교차 엣지 포함 |
| 5 | 공정 구간 센서 판독값 | 시계열 바인딩 | **Lakehouse+Kusto** | 미확인 |

**질문 3·4는 현재 실행할 수 없습니다.** 질문 3이 앞서 답변을 낸 것은 교차 엣지 없이 답할 수 있는 부분만 처리한 결과로 보이며, 설비 유형과 공정 시간이 실제로 나왔는지 재확인해야 합니다. 부분 답변을 성공으로 기록하지 않습니다.

질문 5는 교차 **관계**가 아니라 `Equipment` 한 엔터티의 **시계열 바인딩**이므로 별개 경로입니다. 다만 공정 구간을 얻으려면 `EquipmentHasRuns`(MES 내부, 동작 확인됨)만 쓰면 되므로 시도할 수 있습니다.

### 질문 0. 부적합 분포 (관계 0개, 안전장치)

```text
적재된 전체 부적합 기록을 발생 출처 구분값별로 건수를 세줘. 출처마다 담당 부서별 건수와, 건수가 많은 결함 코드 상위 5개를 코드와 건수로 보여줘. Nonconformance 엔터티의 속성만 사용하고 다른 엔터티와 연결하지 마. 결함 코드의 상위 분류는 이 엔터티에 없으니 요구하지 말고, 필요한 속성이 조회 결과에 없으면 같은 엔터티에서 그 속성을 포함해 다시 조회해줘. 로트 ID·검사 ID·입고검사 ID가 비어 있는 건수도 각각 따로 표시해줘.
```

**역할:** NL2SQL 차별성은 없습니다. 엔터티 읽기가 정상임을 확인하는 사전 점검이며, 뒤 질문이 모두 실패해도 실습이 중단되지 않도록 하는 안전장치입니다.

**확인 기준:** 발생 출처는 `ncr_source` 값(공정검사·입고검사·출하검사·고객제기)으로 구분합니다. `inspection_id`·`iqc_id`·`lot_id` 중 무엇이 채워졌는지로 출처를 추론하지 않습니다. NCR은 출처에 따라 이 셋 중 하나만 채워지는 구조이므로 null이 많은 것은 결함이 아닙니다. `defect_category`는 DefectCode 엔터티에만 있으므로 이 질문에서 요구하지 않습니다. 담당 부서 컬럼은 `owner_dept_ko`이며, 에이전트가 존재하지 않는 이름을 만들어 쓰지 않는지 확인합니다. 로트·검사 엔터티로 조인을 시도하면 지침이 반영되지 않은 것입니다.

### 질문 1. 처리 승인 상태 (관계 1개, QMS 내부)

```text
적재된 전체 부적합 기록 중 처리 결정이 등록된 건을 찾아, 부적합의 담당 부서·조치 기한과 처리 결정 종류·승인 상태를 함께 정리해줘. 승인이 끝나지 않은 건을 먼저 보여주고, 처리가 연결되지 않은 부적합 건수도 따로 표시해줘.
```

**관계:** `NcrHasDisposition` (QMS → QMS).

**역할:** 진단용 A/B 테스트입니다. 같은 Lakehouse 안의 관계가 동작하는지 확인해, 실패 범위가 **관계 전반**인지 **저장소 교차**인지 가릅니다. NL2SQL도 같은 답을 냅니다.

**확인 기준:** `Disposition`은 `ncr_id`를 자체 속성으로 가지므로 ID 나열만으로는 관계가 필요 없습니다. 부적합의 담당 부서·기한을 같이 요구해야 관계 사용이 강제됩니다. `LotHasDisposition` 경로와 합산하지 않는지 확인합니다. 실제 승인 상태값을 먼저 확인하고 추측한 문자열로 필터링하지 않는지 봅니다.

### 질문 2. 담당 역할 구분 (관계 2개, QMS 내부)

```text
적재된 전체 검사 기록에서 검사를 담당한 사람과 측정값을 기록한 사람이 서로 다른 건을 찾아줘. 두 사람의 이름·소속 팀·자격 등급을 각각 구분해서 보여주고, 두 사람이 같은 건수도 함께 알려줘.
```

**관계:** `InspectorDoesInspection`(`inspector_id`), `InspectorRecordsMeasure`(`measured_by`). **2개입니다.** `Measurement`가 `inspection_id`를 자체 속성으로 가지므로 `InspectionHasMeasures`는 필요하지 않습니다.

**역할:** 같은 `Inspector`를 **서로 다른 역할로 두 번** 사용합니다. SQL로도 가능하지만 self-join 두 번을 사람이 설계해야 하고, 컬럼명이 `inspector_id`와 `measured_by`로 달라 경로를 틀리기 쉽습니다.

**확인 기준:** 연결된 측정마다 두 사람의 ID를 비교합니다. `metrology_eqp_id`를 사람 ID로 대신하지 않는지 확인합니다. 연결 누락을 불일치로 계산하지 않으며, 역할 분담 자체를 과실로 해석하지 않습니다.

### 질문 3. 설비 유형별 공정과 검사 (교차, 핵심)

```text
적재된 전체 공정실행을 설비 유형별로 묶어, 각 유형에서 수행된 공정검사 건수와 불합격 건수를 집계해줘. 공정실행의 시작·종료 시각 범위도 함께 보여주고, 검사가 연결되지 않은 공정실행 건수는 따로 표시해줘.
```

**관계:** `EquipmentHasRuns`(MES 내부) + `RunHasInspection`(교차).

**NL2SQL이 못 하는 이유:** `eqp_type`은 `mes_equipment`에만, `in_time`·`out_time`은 `mes_process_result`에만, `judgment`는 `qms_inspection`에만 있습니다. 세 테이블이 **두 개의 서로 다른 Lakehouse**에 나뉘어 있습니다. QMS만 보는 질의는 설비 유형과 공정 시간을 모르고, MES만 보는 질의는 판정을 모릅니다.

**확인 기준:** `qms_inspection`에 `eqp_id`·`step_code`·`product_code`가 복사되어 있으므로, **설비 유형과 시간 구간이 답변에 실제로 나왔는지** 확인해야 우회가 아님을 알 수 있습니다. 같은 공정이 여러 검사에 연결돼도 공정 수는 한 번만 셉니다. 검사 종류가 섞이면 IPQC·IPQC-RT·OQC를 구분했는지 봅니다.

### 질문 4. 설비 유형별 부적합 (교차, 대체 경로)

```text
공정검사에서 발견된 부적합을 대상으로, 그 검사가 수행된 공정실행의 설비 유형별로 묶어 심각도별 건수와 추정 비용 합계를 보여줘. 부적합에서 검사, 검사에서 공정실행, 공정실행에서 설비 순서로 연결해줘. 검사나 공정실행에 연결되지 않은 부적합은 제외하지 말고 건수를 따로 표시해줘.
```

**관계:** `InspectionHasNcr`(QMS 내부) + `RunHasInspection`(교차) + `EquipmentHasRuns`(MES 내부).

**원래 경로를 쓰지 않는 이유:** `EquipmentHasNcr` 한 엣지가 그래프에서 조회되지 않습니다. 오류 원문은 4단계에 기록했습니다. 대체 경로는 질문 3에서 **이미 동작이 확인된 엣지만** 사용합니다.

**NL2SQL이 못 하는 이유:** `eqp_type`은 MES Lakehouse에, `severity`·`estimated_cost_krw`는 QMS Lakehouse에 있습니다. 설비 **개별 ID**로는 QMS만으로도 집계되지만 **유형**으로는 되지 않습니다. 3-hop 경로라 원래 질문보다 오히려 그래프 탐색을 더 잘 보여줍니다.

**확인 기준:** 대상이 `ncr_source`가 공정검사인 NCR로 한정되므로 전체 부적합보다 적게 나옵니다. 이는 실패가 아닙니다. 비용은 `estimated_cost_krw`를 NCR ID마다 한 번만 계산하고 `scrap_cost_krw`와 합치지 않습니다. 같은 공정실행에 여러 NCR이 걸려도 설비 유형 집계에서 NCR을 중복으로 세지 않습니다. 결함 카테고리까지 보려면 `DefectInNcr`(QMS 내부)를 한 번 더 걸어야 하며, 이 엣지는 아직 검증되지 않았습니다.

### 질문 5. 공정 구간의 센서 판독값 (Lakehouse + Kusto, 미검증)

```text
설비 한 대를 골라 공정실행 한 건의 시작 시각부터 종료 시각 사이에 기록된 센서 판독값을 보여줘. 센서 코드와 단위를 구분해서 표시하고, 같은 시각에 여러 센서가 있으면 합치지 말고 원본 행 그대로 보여줘.
```

**바인딩:** `Equipment`의 정적 바인딩(Lakehouse Delta)과 시계열 바인딩(Kusto), `EquipmentHasRuns`.

**NL2SQL이 못 하는 이유:** Lakehouse Delta 테이블과 Eventhouse KQL 테이블을 한 엔터티에 붙인 결과입니다. SQL로는 접근 경로 자체가 없습니다. **온톨로지만 가능한 유일한 영역입니다.**

**확인 기준:** [노트북](manufacturing_ontology.ipynb)이 이 직접 바인딩의 실제 질의를 미검증으로 명시합니다. `in_time <= reading_ts < out_time`은 관계가 자동 계산하지 않으므로 질의에서 명시해야 합니다. `sensor_code`·`unit`·`reading_ts`·`value`·`status`가 같은 원본 행에 대응하는지 먼저 확인하기 전에는 데모 성공 항목으로 잡지 않습니다. `CHAMBER_TEMP`와 `AMBIENT_TEMP`를 합치지 않으며, 센서 규격의 정상 범위·경보 한계는 온톨로지에 바인딩되지 않았으므로 규격 대비 이탈량을 묻지 않습니다.

### 남은 확인 사항

공식 문서에는 이 제약이 기재돼 있지 않습니다. [관계 유형 문서](https://learn.microsoft.com/en-us/fabric/iq/ontology/how-to-create-relationship-types)는 매핑 테이블이 OneLake에 있고 양쪽 키를 포함할 것만 요구합니다. 따라서 preview 단계의 미문서화 제약인지, 이 환경 고유의 문제인지는 확정되지 않았습니다.

**아직 시험하지 않은 것:** origin이 QMS이고 target이 MES인 **역방향** 관계입니다. 실패한 6개는 전부 origin이 MES이므로, 방향을 뒤집으면 origin과 매핑 테이블이 같은 Lakehouse가 됩니다. 제약이 origin 쪽에만 걸리는지 양쪽 모두인지는 이 시험으로만 알 수 있습니다.

원인이 확정되기 전에 온톨로지를 덮어쓰지 않습니다. 집계 결과를 외부에서 계산해 온톨로지에 적재하는 방식은 이 실습의 범위가 아니며, 원본 테이블도 변경하지 않습니다.

## 사용 방법과 범위

**각 코드 블록이 독립적인 질문 하나입니다.** 원하는 질문 전체를 데이터 에이전트에 한 번에 전달합니다. 앞선 대화에서 로트·설비를 고르거나 기간을 설정할 필요가 없으며, 다른 질문의 결과도 필요하지 않습니다. 에이전트 내부에서는 여러 조회가 필요할 수 있지만 사용자가 연결 순서를 안내하지 않습니다.

[온톨로지 노트북](manufacturing_ontology.ipynb)의 기존 MES·QMS·FDC와 **11개 엔터티·18개 관계**를 사용합니다. 온톨로지를 연결한 에이전트에 [공통 지침](data-agent-instructions.txt)을 적용한 상태를 전제로 합니다. 에이전트 생성·온톨로지 연결은 이 문서에서 수행하지 않습니다.

질문은 업무 용어로 기간·대상·분석 목적을 전달합니다. **기술적인 경로와 확인 기준은 진행자용이며 질문에 붙여 넣지 않습니다.** 일반 NL2SQL도 같은 결과를 낼 수 있지만, 여기서는 업무 관계를 모델에 맡겨 품질 기록·생산 구간·설비 관측을 연결하는 데 초점을 둡니다.

| 질문 | 한 번에 결합하는 업무 근거 | 현재 판단 |
|---|---|---|
| 1. 불량별 온도와 연관 불량 | 불량 분류 + 검사 + 생산 구간 + 온도 + 다른 불량 | 사용자 실행: 답변 실패. 관계・센서 질의 실패를 에이전트가 보고 |
| 2. 출하 품질 재검토 | 출하검사 + 미결 품질 문제 + 생산 근거 + 처리 상태 | 사용자 실행: 답변 실패. 원본 오류 미확보 |
| 3. 재작업 실패 비용 | 처리비용 + 부적합 + 검사 + 공정·설비 + 반복 결함 | 사용자 실행: 답변 실패. ProcessRun–Inspection 연결 거부를 에이전트가 보고 |
| 4. 설비 점검 우선순위 | 동일 제품·공정 + 설비별 품질 + 생산 중 센서 경보 | 성공 미확인. 시연 사용 보류 |
| 5. 측정 신뢰성 조사 | 불합격 + 같은 공정의 재검사 + 측정·규격 + 담당 역할 | 성공 미확인. 시연 사용 보류 |

- 다음 진단은 에이전트에 연결된 실제 온톨로지와 도구가 조회한 스키마, 실패한 호출의 입력·생성 질의·원본 오류를 대조하는 것입니다. 원인 확인 전 관계 정의·권한·프롬프트를 추측으로 변경하지 않습니다.

## 1. 불량 코드별 평균 온도와 연관 불량 - 답변 못함

**업무 목적:** 어떤 불량이 어떤 생산 온도 구간에서 관측됐는지, 같은 조건에서 다른 불량도 나타났는지 함께 살펴봅니다.

```text
최근 10일간 공정검사에서 발견된 불량 코드별로 생산 당시 평균 챔버 온도는 얼마야? 같은 제품·공정에서 비슷한 온도 구간에 나타난 다른 불량 코드도 함께 찾아줘.
```

**관계 경로:** `DefectCode -> Nonconformance <- Inspection <- ProcessRun <- Equipment`, `ProductionLot -> ProcessRun`. 온도는 Equipment의 시계열에서 해당 공정의 가동 구간으로 연결합니다.

**기대 결과:** 불량 코드·제품·공정·설비 유형별 평균 챔버 온도, 공정 수·관측 수, 비교한 온도 구간, 그 구간의 다른 불량 코드와 근거 공정·검사·NCR ID.

**진행자 확인:**

- 최근 10일은 기본 IPQC의 검사시각으로 대상을 고르고, 그 검사에 연결된 NCR의 `defect_code`를 사용합니다. 불합격이어도 코드나 공정 연결이 없으면 분류 불가로 남깁니다. 생산 온도는 검사시각의 온도가 아니라 연결된 공정의 가동 구간에서 가져옵니다.
- [FDC 샘플](../2.fdc-eventhouse/fdc_eventhouse_stream.ipynb)에 `CHAMBER_TEMP`가 있지만 모든 설비에 있는 센서는 아닙니다. 없는 경우 주변 온도로 대체하지 않습니다. Furnace·Etcher·CVD는 같은 센서 코드여도 운전 온도가 다르므로 제품·공정·설비 유형·센서·단위를 구분합니다.
- 공정별 Run 관측의 평균을 먼저 구한 뒤, 불량 코드별로 고유 공정 평균의 평균을 계산하는 방식을 확인 기준으로 사용합니다. 같은 공정이 여러 검사·NCR에 연결돼도 해당 코드 안에서 한 번만 셉니다. 평균의 가중 방식과 표본 수가 답변에 명시되어야 합니다.
- “비슷한 온도”의 범위는 온톨로지에 정의되어 있지 않습니다. 에이전트가 비교 기준을 밝히는지 확인하며, 기준이 불명확하면 범위를 확인해야 합니다. 리허설에서는 동일 비교 집단 내 기준 불량의 공정 평균 온도 최솟값~최댓값을 관측 범위로 삼아 대조할 수 있습니다. 이를 정상 범위나 불량 발생 임계값이라고 표현하지 않습니다.
- 다른 불량은 같은 검사 기간·제품·공정·설비 유형·센서·단위 조건에서 찾습니다. 같은 공정에 함께 기록된 다른 코드인지, 별도 공정에서 같은 온도 범위에 관측된 코드인지 구분합니다. 관측 범위가 넓거나 사례가 적으면 연관성을 과장하지 않습니다.

## 2. 출하검사 합격 로트의 미완료 품질 문제 - 답변 못함

**업무 목적:** 출하검사 합격 기록만으로 놓칠 수 있는 미결 품질 문제와 처리 상태를 생산 근거까지 연결해 검토합니다.

```text
최근 10일간 출하검사에 합격한 로트 중 아직 품질 조치가 끝나지 않은 로트를 찾아줘. 남아 있는 불량이 어느 생산 공정·설비와 연결되는지, 처리와 승인은 어디까지 진행됐는지 함께 정리해줘.
```

**관계 경로:** `ProductionLot -> Inspection -> Nonconformance -> Disposition`, `Equipment -> ProcessRun -> Inspection`. 로트에 직접 연결된 NCR도 함께 확인합니다.

**기대 결과:** 로트별 OQC 판정 구성, 미결 NCR, 연결된 공정·설비, 처리유형·승인 상태·담당 부서·기한과 근거 ID.

**진행자 확인:** 최근 10일의 OQC 합격 기록으로 로트를 선택한 뒤 해당 로트의 전체 OQC·품질 조치를 확인합니다. 미결 NCR 또는 처리 승인 대기·반려를 미완료로 보고, null·미확정 상태는 따로 표시합니다. NCR의 발견 검사는 OQC와 다를 수 있습니다. 그 검사에서 공정으로 연결되지 않으면 로트가 거친 임의의 설비를 배정하지 않습니다. 결과는 적재된 품질 기록의 검토이며 실제 출하 여부·최종 출하 승인·홀드를 의미하지 않습니다.

## 3. 재작업 실패 비용과 반복 불량 - 답변 못함

**업무 목적:** 폐기 비용이 집중된 생산 영역과 그곳에서 반복되는 불량 유형을 함께 찾아 개선 검토 대상을 정합니다.

```text
최근 10일간 재작업에 실패해 폐기 처리된 건들의 비용은 어느 생산 공정과 설비에 집중돼 있어? 비용이 큰 곳에서 반복된 불량 유형과 기록된 조치도 함께 정리해줘.
```

**관계 경로:** `Equipment -> ProcessRun -> Inspection -> Nonconformance -> Disposition`, `DefectCode -> Nonconformance`

**기대 결과:** 승인 상태를 구분한 공정·설비별 폐기 비용, 고유 처리·NCR 수, 반복 결함과 기록된 원인·즉시조치, 귀속 불명·비용 누락 항목.

**진행자 확인:** 최근 10일은 처리 결정일로 선택합니다. 비용은 `scrap_cost_krw`를 처리 ID마다 한 번만 계산하고 `estimated_cost_krw`와 합치지 않습니다. 같은 로트의 모든 설비가 아니라 해당 NCR·검사에서 실제 연결되는 공정으로 귀속합니다. 연결이 없거나 모호하면 별도 집계합니다. 같은 NCR에 여러 처리건이 있으면 비용은 각 처리건 기준, 반복 불량은 고유 NCR·공정 기준으로 구분합니다. 전체 집계 전에 상위 행을 잘라내지 않으며 실제 재작업 시간·회계상 실현 손실은 추정하지 않습니다.

## 4. 품질 결과와 센서 경보를 함께 보는 설비 점검

**업무 목적:** 같은 제품·공정을 처리하는 설비들의 품질 결과와 생산 당시 관측을 비교해 점검 우선순위의 근거를 마련합니다.

```text
최근 10일간 같은 제품을 같은 공정에서 처리한 설비들의 공정검사 불합격 비율과 생산 중 센서 경보 비율을 비교해줘. 두 지표와 관련된 불량 유형을 근거로 먼저 점검할 설비를 최대 3개 추천해줘.
```

**관계 경로:** `Equipment -> ProcessRun <- ProductionLot`, `ProcessRun -> Inspection -> Nonconformance <- DefectCode`. 경보는 Equipment의 시계열로 조회합니다.

**기대 결과:** 제품·공정별 설비 비교표, 기본 IPQC 불합격 비율, 센서별 Alarm 표본 비율과 각 분자·분모, 관련 결함·NCR, 추천 이유와 자료 부족 항목.

**진행자 확인:** 최근 10일에 종료된 공정실행을 대상으로 같은 제품·공정 코드를 맞춥니다. 연결된 기본 IPQC의 고유 불합격 검사 수 / 고유 검사 수로 비교하고 IPQC-RT는 분리합니다. 경보 비율은 해당 생산 구간의 센서별 Run 상태 Alarm 행수 / Run 상태 전체 관측 행수이며 지속시간 비율이 아닙니다. 센서·단위를 섞거나 겹치는 공정 구간의 관측을 중복 집계하지 않습니다. 분모 0·미관측·조회 실패를 0%로 채우지 않습니다. 두 지표를 임의 종합 점수로 합치지 않고 비교 표본·미확인 조건을 표시합니다. 같은 코드가 같은 레시피·설정이나 인과적 비교를 보장하지는 않습니다.

## 5. 측정 문제로 기록된 불합격의 판정 근거

**업무 목적:** 측정 관련 불합격이 재검사에서 어떻게 나타났는지, 어떤 규격과 담당 기록으로 확인할 수 있는지 한 번에 조사합니다.

```text
최근 10일간 측정 문제로 기록된 공정검사 불합격 사례에서 같은 공정의 재검사 결과는 어땠어? 측정값·적용 규격·검사 및 측정 담당 기록을 대조해서 추가 확인이 필요한 사례를 정리해줘.
```

**관계 경로:** `ProcessRun -> Inspection -> Nonconformance`, `Inspector -> Inspection -> Measurement <- InspectionSpec`, `Inspector -> Measurement`

**기대 결과:** 기본 검사와 같은 공정의 재검사 ID·판정, 측정값·규격·이탈 여부, 검사원과 측정 담당자, 기록상 차이와 근거가 부족한 항목.

**진행자 확인:** 최근 10일의 기본 IPQC 불합격에서 연결된 NCR의 원인 분류가 측정인 기록을 선택합니다. 같은 ProcessRun의 IPQC-RT를 조회하되 특정 기본 검사의 직접 후속 관계라고 단정하지 않습니다. 규격은 `spec_id`로 연결하고 제품·공정·특성이 다른 규격을 섞지 않습니다. 검사 담당자는 InspectorDoesInspection, 측정 담당자는 InspectorRecordsMeasure로 구분합니다. 기본 검사에 개별 측정값이 없거나 두 담당자가 같아도 그 자체로 오류는 아닙니다. 재검사·측정·규격 연결이 없으면 근거 부족으로 표시하며 검사원 과실로 해석하지 않습니다.

## 진행자용 기간·FDC 검증 기준

아래는 사전 리허설과 답변 확인을 위한 내용이지, 참가자가 순서대로 입력해야 하는 준비 질문이 아닙니다.

- **실행 준비:** 온톨로지 Graph 갱신·인스턴스 조회, 에이전트의 소스 연결과 실행 계정의 조회 권한을 확인합니다. 질문 1·4는 FDC의 센서별 필터와 행 대응, 집계가 실제로 작동하는지 확인해야 합니다. 노트북이 생성되었다는 사실로 실행 성공을 대신하지 않습니다.
- **최근 10일:** 질문 실행 시점 기준이며 시작·종료 시각과 시간대를 답변에 표시합니다. 날짜만 있는 처리 결정일은 날짜 단위 경계를 명시합니다. 연관 생산·검사·조치 기록에 같은 기간 필터를 무조건 적용하지 않습니다. 예를 들어 최근 검사에 대응하는 생산은 더 이전일 수 있습니다.
- **과거 샘플:** 최근 10일에 데이터가 없으면 0건 또는 기간 내 자료 없음으로 답해야 합니다. 시연에 과거 데이터가 필요하면 진행자가 실제 날짜를 확인해 질문의 “최근 10일간”을 명시적 날짜 구간으로 바꿉니다. 에이전트가 임의로 마지막 데이터 시점 기준으로 바꾸면 안 됩니다.
- **생산 관측:** 같은 `eqp_id`에서 `in_time <= reading_ts < out_time`이고 `run_status = Run`인 관측만 사용합니다. 검사·OQC 시각을 생산 구간 대신 쓰지 않습니다. 같은 관측이 여러 공정에 걸리면 귀속 모호성과 중복을 확인합니다.
- **센서 구분:** 시계열 속성은 `Eqp_sensor_code`, `Eqp_unit`, `Eqp_reading_ts`, `Eqp_value`, `Eqp_status`, `Eqp_run_status`입니다. 값·상태·시각을 같은 원본 행으로 대조합니다. `CHAMBER_TEMP`와 `AMBIENT_TEMP`를 합치지 않으며 설비 유형별 범위 차이도 구분합니다.
- **한계:** `fdc_sensor_spec`의 정상 범위·경보 한계는 온톨로지에 바인딩되지 않았습니다. 기록된 status와 관측값을 사용하며 규격 대비 온도 이탈량이나 기대 표본 대비 누락률을 안다고 가정하지 않습니다. “비슷한 온도”의 해석도 질의에서 명시해야 하며 모델이 자동 결정하는 기준이 아닙니다.

관계 경로의 화살표는 등록된 정방향이며 질의는 역으로 탐색할 수도 있습니다. 원본 테이블의 로트·설비 코드만 출력했다고 경로를 확인한 것은 아닙니다. 중간 검사·NCR·공정 ID를 대조하고 가능한 경우 실행 질의·도구 결과도 확인합니다.

## 리허설 완료 기준과 정리

**사용자는 한 번 묻고, 에이전트가 필요한 대상 탐색·연결·집계·비교를 수행하는지** 확인합니다. 앞선 질문에서 고른 ID나 이전 대화의 기간 설정에 의존하는지 점검하기 위해 각 질문을 새 대화에서도 시험합니다. 이 문서의 진행자 설명은 에이전트에 자동 전달되지 않습니다.

| 확인 항목 | 확인 방법 |
|---|---|
| 관계·기간 | 실제 ID와 각 질문의 날짜 기준을 원본 MES·QMS와 대조 |
| 집계·비교 | 전체 대상에서 계산한 건수·비율·비용·온도 평균과 비교 범위를 대조. 중복·잘린 결과 집계 배제 |
