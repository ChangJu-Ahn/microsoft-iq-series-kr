# Factory Ontology 비즈니스 시나리오

## 목적과 모델

생산 이력, 품질 기록, 설비 센서 관측을 업무 관계로 연결해 조사하는 실습입니다. 기존 문서의 기본 질문 중 동일한 부적합 처리·승인 조회를 합쳐 기본 질문 5개와 상세 시나리오 5개로 정리했습니다. 현재 [온톨로지 노트북](03_manufacturing_ontology.ipynb)을 사용하며 새로운 데이터나 시나리오를 생성하지 않습니다.

| 소스 | 물리 테이블 | 엔터티 |
|---|---|---|
| factory_lakehouse의 `mes` 스키마 | `equipment`, `lot`, `process_result` | Equipment, ProductionLot, ProcessRun |
| 같은 Lakehouse의 `qms` 스키마 | `inspector`, `inspection_spec`, `inspection`, `measurement`, `defect_code`, `incoming_inspection`, `nonconformance`, `disposition` | Inspector, InspectionSpec, Inspection, Measurement, DefectCode, IncomingInspection, Nonconformance, Disposition |
| 별도 FDC Eventhouse | `fdc_sensor_reading` | Equipment의 시계열 속성 |

모델은 정적 엔터티 11개, 관계 18개, Equipment 시계열 속성 6개로 구성됩니다. `fdc_sensor_spec`은 원본 검사에만 사용하며 별도 엔터티가 아닙니다. 계산 속성·인과 추론 규칙·실제 자재 투입 계보는 포함하지 않습니다.

MES·QMS는 같은 Lakehouse에 있으므로 SQL 조인으로도 같은 결과를 구할 수 있습니다. 이 실습의 초점은 SQL의 불가능성을 입증하는 것이 아니라, 등록된 업무 관계·역할·키를 사용해 답변 근거를 추적하고 Eventhouse 시계열까지 연결하는 데 있습니다. 엔터티 설명의 경고는 질의 지침이지 잘못된 조인을 기술적으로 차단하는 제약은 아닙니다.

## 준비와 적용

1. [factory_lakehouse](01_factory_lakehouse.ipynb)와 [FDC Eventhouse](02_fdc_eventhouse.ipynb)의 데이터 적재를 완료합니다. 같은 Mock MES 주소와 이력을 사용하고 기존 날짜·시드·생성 규칙은 변경하지 않습니다.
2. [온톨로지 노트북](03_manufacturing_ontology.ipynb)에서 소스 검증·정의 게시·Graph 새로 고침을 완료합니다. 최신 모델 로드 후 새 Queryset에서 출력된 18개 관계의 실제 건수를 기대 건수와 대조합니다.
3. Fabric 용량과 필요한 사용 설정·조회 권한을 갖춘 작업 영역에서 Data Agent를 준비하고 **이번에 만든 온톨로지**를 소스로 연결합니다. 기본 이름은 `Factory_Ontology`이나 실행 시 출력한 실제 이름·ID를 확인합니다. 기존 온톨로지나 Lakehouse 단독 소스를 대신 선택하지 않습니다.
4. [데이터 에이전트 지침](data-agent-instructions.txt) 전문을 적용하고 저장합니다. 게시된 에이전트를 사용할 경우 Publish 후 해당 버전을 확인합니다. 로컬 파일 수정은 원격 에이전트 설정을 바꾸지 않습니다.
5. 각 질문을 **새 대화에서 한 블록씩** 전달합니다. 질문 0의 선택적 후속 필터는 같은 대화에서 이어서 사용할 수 있습니다. 기술 설명과 확인 기준은 진행자용이며 질문에 붙여 넣지 않습니다. 확장 A·D에서는 기본 질문 4를 넘어 공정 구간별 센서 조회·집계까지 추가로 검증합니다. 이 부분이 실패하면 정적 데이터만으로 전체 질문을 통과 처리하지 않습니다.

이 문서는 에이전트 생성·연결을 자동 수행하지 않습니다. 권한 오류가 발생하면 실제 도구 오류와 실행 신원을 확인하며, 실습을 통과시키기 위해 권한·보안 설정을 임의로 완화하지 않습니다.

## 검증 상태

**기본 질문 1~4는 사용자 확인에 따라 검증 완료한 것으로 두고, 이제 확장 A~E를 시험합니다(2026-09-17).** 질문 0은 사용자 제공 답변의 항목 충족과 목록 완전성을 확인했습니다. 기본 질문의 검증과 별개로 확장 시나리오는 아직 실행 미검증이며, 새로 요구하는 집계·비교·시간 구간 매칭은 각각 확인해야 합니다. 이 문서에 기록된 답변 확인은 작성자의 원본 데이터·실행 질의 대조를 뜻하지 않습니다. 이전 센서 원본 행 조회 실패나 전체 집계 문제까지 해결된 것으로 간주하지 않습니다.

| 단계 | 확인 대상 | 완료 기준 |
|---|---|---|
| 데이터 | MES·QMS·FDC | 생성 노트북의 검증 통과, 같은 이력·키·시간 기준 |
| Graph | 정적 관계 18개 | 새 Queryset의 실제 관계 건수와 원본 기대 건수 일치 |
| 기본 질문 | 0~3 | 원본 ID·집계와 일치하고 요청 항목을 빠짐없이 반환 |
| 시계열·공정 연결 | 질문 4 | 가동 중 경보 이력이 있는 설비 집합과 연결된 생산 이력이 원본과 일치하고, 표시 범위가 명확함 |
| 확장 질문 | A~E | 다단계 연결·중복 제거·기간·집계 기준과 원본 결과 일치 |

정의 게시, Graph 작업 완료, 실제 관계 조회, Data Agent 응답 검증은 별도 단계입니다. 예전 오류 메시지만으로 교차 Lakehouse 제약이나 권한 문제를 확정하지 않습니다.

## 기본 질문

질문 0~3은 정적 업무 관계 점검, 질문 4는 시계열 점검입니다. 실패하면 같은 질문의 실행 질의·원본 오류부터 확인합니다. 다른 질문의 성공으로 실패한 질문을 통과 처리하지 않습니다.

### 질문 0. 부적합 처리·승인 현황

```text
처리 결정이 등록된 부적합을 찾아줘.
각 부적합의 ID·발생 출처·담당 부서와,
연결된 처리 결정의 종류·승인 상태를 함께 보여줘.
```

**목적:** Nonconformance의 부적합 정보와 Disposition의 처리 정보를 온톨로지 관계로 연결해 현황을 조회하고, 필요하면 승인 검토가 남은 건과 조치 기한을 확인합니다. 전체 목록과 승인 필터는 같은 업무 개념의 기본 조회·후속 조회이며 별도 시나리오로 나누지 않습니다. 복합 집계·순위·미연결 건수 집계는 함께 요구하지 않습니다.

**선택적 후속 필터:** 승인 검토가 남은 건만 보고 싶을 때 사용합니다. 조치 기한이 기존 결과에 없다면 추가 조회가 필요하며, 아래 문구는 새 대화에서도 독립적으로 사용할 수 있습니다.

```text
처리 결정의 승인 상태가 대기 또는 반려인 부적합을 찾아줘.
부적합 ID·담당 부서·조치 기한과,
연결된 처리 결정의 ID·종류·승인 상태를 함께 보여줘.
```

**관계:** `Nonconformance -> Disposition`의 `NcrHasDisposition`.

**확인 기준:**

- 부적합의 `ncr_id`·`ncr_source`·`owner_dept_ko`와 연결된 처리의 `disposition_type`·`approval_status`를 반환합니다. 이는 원본 컬럼명이며 실행 속성명은 실제 온톨로지 스키마를 확인합니다.
- 원본의 `Disposition.ncr_id`와 `Nonconformance.ncr_id`로 대응을 확인합니다. `disposition_id`도 함께 반환되면 쌍을 대조하기 쉽습니다. ID의 숫자 접미사가 같다는 이유만으로 연결을 추정하지 않습니다.
- 같은 `(ncr_id, disposition_id)` 쌍을 중복 표시하지 않습니다. 기본 생성 데이터는 NCR 95건과 처리 95건의 1:1 구조이지만, 실제 판정은 현재 저장된 데이터와 대조합니다. 결과가 잘렸다면 전체 목록이라고 표현하지 않습니다.
- 승인·대기·반려를 실제 값대로 표시하고, 처리 결정이 등록됐다는 사실을 승인 완료로 해석하지 않습니다. 부적합의 발생 출처·담당 부서와 처리의 승인 상태를 혼동하지 않습니다.
- 후속 필터는 `Disposition.approval_status`가 `대기` 또는 `반려`인 건만 반환하고 `Nonconformance.due_date`를 함께 확인합니다. NCR 자체 상태로 대신 필터링하지 않습니다. 날짜는 실제 저장값과 대조하며, 조회하지 않은 기한을 추정하지 않습니다.
- 실제 실행 질의에서 `NcrHasDisposition`을 사용했는지 확인합니다. 자연어 답변에 두 ID가 나열됐다는 사실만으로 관계 사용을 확정하지 않습니다.

**현재 확인 결과 (2026-09-17):** 사용자 제공 답변에는 요청 항목과 처리 ID가 포함됐으며, 고유 NCR 95건(`NCR-2026-0001`~`NCR-2026-0095`)에 누락·중복이 없었습니다. 출처별 분포는 공정검사 43건·입고검사 40건·출하검사 6건·고객제기 6건으로 기본 생성 기준과 일치했습니다. 행별 부서·처리 종류·승인 상태의 원본 대조와 실제 관계 사용은 미확인이므로 판정은 **부분 확인**입니다. 이전 복합 집계 질문의 문제까지 해결됐다는 뜻은 아닙니다.

**후속 필터 확인 결과 (2026-09-17):** 사용자 제공 답변은 대기 7건·반려 7건, 총 14건이며 부적합 ID·처리 ID·담당 부서·처리 종류·승인 상태가 앞선 95건 목록과 일치했습니다. 조치 기한은 추가로 반환됐으나 원본 대조는 미확인입니다. 실제 관계 사용도 미확인이므로 **부분 확인**으로 기록합니다. 두 답변 간 일치가 원본 데이터 검증을 대신하지 않으며, 이전 미연결 집계 `9025건`의 원인이 해결됐다는 의미도 아닙니다.

### 질문 1. 검사·측정 담당 역할

```text
검사별 측정 결과와 검사 담당자·측정 기록자의 소속 및 자격을 함께 조회해서 같이 보여줘.
```

**목적:** 측정 기록이 있는 검사의 측정 특성·값과 검사 담당자·측정 기록자의 이름·소속 팀·자격 등급을 역할별로 확인합니다. 업무 질문에서 검사·측정·담당자 관계를 에이전트가 찾아 사용하는지 확인하며, 두 역할의 담당자가 같아도 정상입니다. 전체 건수나 측정 없는 검사 집계는 요구하지 않습니다.

**관계:** `InspectorDoesInspection`, `InspectionHasMeasures`, `InspectorRecordsMeasure`.

### 질문 2. 검사의 생산 공정과 사용 설비

```text
공정검사와 재검사 결과를 생산 이력 및 사용 설비와 함께 결과만 표 형태로 보여줘
```

**목적:** 공정검사(IPQC)와 재검사(IPQC-RT)의 판정을 해당 공정실행의 시작·종료 시각 및 사용 설비의 유형과 함께 확인합니다. 같은 Lakehouse의 QMS 검사와 MES 공정·설비 정보를 에이전트가 관계로 연결하는 실습이며, 전체 건수·불합격 건수·시간 범위 집계나 미연결 공정 탐지는 요구하지 않습니다.

**관계:** `Equipment -> ProcessRun`의 `EquipmentHasRuns`, `ProcessRun -> Inspection`의 `RunHasInspection`. 검사에서 연결된 공정실행을 확인하고, 그 공정실행에 사용된 설비를 따라갑니다.

### 질문 3. 부적합의 발견 검사와 생산 공정·설비

```text
공정검사에서 발견된 부적합은 어떤 검사와 생산 공정·설비에서 확인됐고, 심각도와 추정 비용은 어땠어?
```

**목적:** 공정검사 출처의 부적합에서 발견 검사와 그 검사가 수행된 생산 공정·사용 설비를 추적하고, 부적합의 심각도·추정 비용을 함께 확인합니다. 질문 2의 검사·공정·설비 연결에 부적합의 발견 근거를 더하는 실습입니다. 생산 연결이 없는 기록은 임의로 연결하지 않고 구분하며, 전체 심각도별 건수·비용 합계나 미연결 건수는 요구하지 않습니다.

**관계:** `Inspection -> Nonconformance`의 `InspectionHasNcr`, `ProcessRun -> Inspection`의 `RunHasInspection`, `Equipment -> ProcessRun`의 `EquipmentHasRuns`. 조회는 부적합에서 시작해 각 관계를 역방향으로 따라 발견 검사·공정실행·설비를 확인합니다. 부적합에 기록된 설비를 직접 조회하는 `EquipmentHasNcr`로 이 경로를 대신하지 않습니다.

### 질문 4. 센서 경보 이력이 있는 설비의 생산 공정

```text
가동 중 센서 경보가 있었던 설비의 생산 이력을 보여줘.
```

**목적:** Eventhouse 센서 관측으로 경보 이력이 있는 설비를 선별하고, 해당 설비의 MES 생산 이력을 조회합니다. 업무 질문에서 필요한 시계열 조건과 관계를 에이전트가 찾아 사용하는지 확인합니다. 경보 발생 시각에 실행 중이던 공정만을 찾는 질문은 아니며, 반환된 각 공정에서 경보가 발생했다거나 불량의 원인이라는 뜻은 아닙니다.

**관계·바인딩:** Equipment의 Eventhouse 시계열 바인딩에서 동일 관측 행의 `run_status = Run`·`status = Alarm` 이력이 있는 설비를 찾고, `Equipment -> ProcessRun`의 `EquipmentHasRuns`로 연결된 공정을 조회합니다. 설비 정보와 공정·로트 ID·실행 시각은 Lakehouse의 정적 데이터입니다. 질문은 출력 컬럼·정렬·건수를 고정하지 않으며, 설비별 요약이나 상세 목록으로 생산 이력을 보여줄 수 있습니다. 일부만 표시했다면 전체 이력이라고 표현하지 않습니다.

## 확장 시나리오

### A. 불량 코드별 생산 온도와 함께 관측된 불량

```text
기본 공정검사에서 발견된 불량 유형별로 생산 당시 평균 챔버 온도를 비교하고, 각 유형에서 관측된 온도 범위에 다른 불량도 있었는지 보여줘.
```

**목적:** 불량 유형별 생산 온도와 함께 관측된 다른 불량을 비교합니다.

**관계:** `DefectInNcr`, `InspectionHasNcr`, `RunHasInspection`, `EquipmentHasRuns`, `LotHasRuns` 및 Equipment 시계열.

### B. 출하검사 합격 로트의 미완료 품질 조치

```text
출하검사에 합격한 로트 중 아직 마무리되지 않은 품질 조치가 있는 로트를 찾아줘. 어떤 문제가 어느 생산 공정·설비와 관련됐고, 담당 부서와 조치 기한·처리 및 승인 상태는 어떤지 함께 보여줘.
```

**목적:** 출하검사 합격 로트에 남아 있는 품질 조치와 생산 근거를 확인합니다.

**관계:** `LotHasInspection`, `LotHasNcr`, `InspectionHasNcr`, `NcrHasDisposition`, `RunHasInspection`, `EquipmentHasRuns`.

### C. 재작업 실패 비용과 반복 불량

```text
재작업에 실패해 폐기된 사례의 비용은 어느 생산 공정·설비에 집중돼 있어? 처리 승인 상태와 반복된 불량 유형, 기록된 원인·즉시조치도 함께 보여줘.
```

**목적:** 재작업 실패 후 폐기 비용이 집중된 생산 공정·설비와 반복 불량을 조사합니다.

**관계:** `NcrHasDisposition`, `InspectionHasNcr`, `RunHasInspection`, `EquipmentHasRuns`, `DefectInNcr`.

### D. 품질과 센서 경보를 함께 보는 설비 점검

```text
같은 제품을 같은 공정에서 생산한 설비들의 공정검사 불합격률과 가동 중 센서별 경보 비율을 비교해줘. 관련 불량 유형을 근거로 점검이 필요한 설비를 최대 3개 추천해줘.
```

**목적:** 같은 제품·공정의 설비별 품질과 센서 경보를 비교해 점검 후보를 찾습니다.

**관계:** `LotHasRuns`, `EquipmentHasRuns`, `RunHasInspection`, `InspectionHasNcr`, `DefectInNcr` 및 Equipment 시계열.

### E. 측정 문제로 기록된 불합격의 판정 근거

```text
측정 문제로 공정검사에서 불합격 처리된 사례의 판정 근거를 확인해줘. 재검사 결과와 측정값·적용 규격, 담당자의 자격을 대조하고 추가로 확인할 내용을 정리해줘.
```

**목적:** 측정 문제로 기록된 불합격의 재검사·규격·담당자 정보를 대조해 판정 근거를 확인합니다.

**관계:** `InspectionHasNcr`, `RunHasInspection`, `InspectionHasMeasures`, `SpecGovernsMeasurement`, `InspectorDoesInspection`, `InspectorRecordsMeasure`.

## 기간과 답변 판정

- 기본 질문과 확장 질문은 적재된 전체 기록을 사용합니다. 고정된 과거 샘플을 최근 날짜에 맞춰 재생성하지 않습니다.
- 최근 10일 등의 조건을 추가한다면 실행 시점 기준입니다. 기간 내 자료가 없으면 0건 또는 자료 없음으로 답하며 마지막 데이터 시점을 현재로 바꾸지 않습니다. 진행자가 과거 구간을 시연하려면 실제 데이터를 확인한 명시적 날짜를 질문에 넣습니다.
- 검사 기준 기간은 `inspection_datetime`, 처리 기준 기간은 `decision_date`, 생산 기준 기간은 ProcessRun 시작·종료 시각을 사용합니다. 관련 생산·검사·조치에 같은 기간을 일괄 적용하지 않습니다.
- 질문에 필요한 속성명은 실제 게시된 스키마에서 확인합니다. `property_name()`은 긴 속성명을 해시로 축약할 수 있으므로 원본 컬럼명에 접두사를 붙여 실행 이름을 만들지 않습니다.
- 질문 4는 동일 관측 행의 `run_status = Run`·`status = Alarm` 조건으로 설비를 선별한 뒤 연결된 공정을 조회하며, 경보 시각과 각 공정 구간의 일치를 요구하지 않습니다. 공정 구간별 시계열을 사용하는 확장 질문에서는 같은 `eqp_id`, `in_time <= reading_ts < out_time`, `run_status = Run` 조건으로 원본 Eventhouse와 대조합니다. 규격 한계나 기대 표본 수가 모델에 있다고 가정하지 않습니다.

| 판정 | 의미 |
|---|---|
| 확인됨 | 요청한 모든 항목·관계·집계가 원본과 일치 |
| 조건 해당 없음 | 조회가 성공했고 전체 대상에서 조건에 맞는 기록이 없음 |
| 부분 확인 | 일부는 확인했으나 관계·속성·시계열 또는 전체 집계가 미확인 |
| 조회 실패 | 도구가 오류를 반환하거나 실행을 완료하지 못함 |

불일치 담당자 0건, 재검사 없음, 연결 없는 NCR은 데이터에 따라 정상입니다. 성공하지 않은 조회를 0건으로 바꾸거나 부분 답변을 전체 성공으로 기록하지 않습니다.

## 실패 기록과 정리

질문별로 실제 온톨로지·Graph·Data Agent 이름과 ID, 실행 시각·시간대, 질문과 필터, 사용한 도구·생성 질의, 비밀값을 제거한 오류 원문, 기대값과 실제값을 기록합니다. 답변의 자연어 추정을 제품 제약이나 권한 오류의 증거로 삼지 않습니다. 관계 이름을 추측해 바꾸거나 의미가 다른 경로로 우회해 실패를 숨기지 않습니다.

온톨로지와 Data Agent 소스가 최신인지 확인하고 지침 수정 후에는 저장·필요한 게시를 마친 뒤 새 대화에서 시험합니다. 질문 4의 경보 이력 설비 집합은 원본 KQL 조회와, 연결된 공정 정보는 MES 원본과 대조합니다. KQL 단독 성공을 온톨로지 통합 성공으로 기록하지 않습니다.

실습은 읽기 전용 질문이며 별도 데이터·리소스를 생성하지 않습니다. Graph·Data Agent·Eventhouse 조회는 Fabric 용량을 사용합니다. 종료 후 불필요한 세션·스케줄을 중지하고, 실습용 에이전트·온톨로지와 관리 하위 항목은 실제 ID와 사용 여부를 확인해 정리합니다. 이 문서나 지침은 자동 삭제를 수행하지 않습니다. 기존 helper 및 원본 리소스의 제거는 v2 원격 검증 완료 후 별도로 진행합니다.

## 기존 문서에서 정리한 내용

- 기존 질문 0·1은 부적합 처리·승인 현황 하나로 통합하고 승인 대기·반려 조회는 선택적 후속 필터로 배치했습니다. 기본 질문 1~4는 업무 언어의 관계 조회로 정리했고, 확장 A~E는 그 관계를 조합해 비교·집계·품질 조치 판단을 묻도록 연결했습니다. 기본 기간은 전체 기록으로 통일하고 최근 기간 사용 규칙은 별도로 명시했습니다.
- 두 Lakehouse 경계 설명을 단일 Lakehouse의 `mes`·`qms` 업무 스키마 설명으로 바꿨습니다.
- NCR 참조가 하나만 채워진다는 오류와 검사·측정 대응 관계가 필요 없다는 단정을 제거했습니다.
- SQL로 불가능하거나 온톨로지만 가능하다는 주장, 경고 설명이 잘못된 조인을 차단한다는 주장을 제거했습니다.
- 서로 모순된 성공·실패 기록, 확인되지 않은 원인 단정, 과거 우회 경로 설명, 중복 정리 문단과 원본 폴더 의존 링크를 제외했습니다. 기존 파일은 변경하지 않았습니다.
